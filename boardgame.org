**** ## 9. Hands and Cards
Hands are Org files. Their card order is defined by the order of their headings.
The package must support any number of hands, with only one active hand at a time.
A hand may belong to a player, an opponent, or another game participant.
### 9.1. Visible and blind hands
A hand may operate in visible or blind mode.

Blind operations must be possible without displaying or revealing the hand's contents. This is required for opponent hands and hidden information.

Commands that manipulate a blind hand must not accidentally expose card names or contents through selection lists, side-log messages, or other incidental displays.

Revealing the contents must be a separate explicit operation.

### 9.2. Hand display
The implementation may use a separate window, bottom panel, existing information pane, or another suitable interface for hand contents.

The exact layout is not fixed.

Where appropriate, the interface should display the active hand, the selected card, and relevant contextual information.

Switching the active hand must not silently alter other hands.

### 9.3. Hand commands
The package must provide commands to:

- Open or create a hand Org file.
- Switch the active hand.
- Add a card or object to a hand.
- Select a card from a visible hand.
- Play the first card.
- Play the last card.
- Play a selected card.
- Play a random card.
- Execute a source block from the active card.
- Execute a source block from the first card by default.
- Execute a source block from a card specified by an explicit index.
- Perform supported operations on a blind hand without revealing its contents.

Card indexing must follow a documented and consistent convention.

### 9.4. Playing cards onto the board
A card may be played at the current cursor position or another explicitly selected position.

If the destination cell contains a permanent container, playing the card must add it to that container instead of placing it visibly on the board.

This is a specific hand-to-board behavior. It must not be confused with stack creation or automatic consolidation.

Whether playing a card consumes it from the hand or copies it must be explicitly defined for each relevant operation. The implementation must not silently duplicate or discard a card when the operation's intended semantics are ambiguous.

## 11. Teleportation
The package must support teleportation to explicit board coordinates and to teleport markers.

Markers may be predefined in board data or placed by the player.

The user must be able to:
- Teleport to specified coordinates.
- Select and teleport to an existing marker.
- Place a marker where supported.
- Edit or remove a player-created marker where supported.

Teleportation must not modify the felt or remove objects from the destination cell.

Invalid coordinates or missing markers must produce a clear message without leaving the cursor in an undefined state.
